# smart-locker

- In the Smart Locker project, `mvnw test` now runs against a separate DB `smart_locker_tester` via src/test/resources/application.properties (create-drop), so tests never touch the shared demo DB; the suite grew from 8 to 32 passing tests, pushed at commit 1028aaf.
- The locker LOCKER_HN_01 (Tủ Giao Nhận KTX A1, Trụ Sở PTIT, Hà Đông) has only 2 physical compartments, so it cannot host more than 2 orders at a time; compartment sizes S/L were removed in 2026-11.
- In the Smart Locker project the backend only starts if the gitignored application-local.properties (which holds the MySQL password) exists locally; when the project is opened on another machine or session the file is missing and the backend fails, so it has to be recreated by hand.
- The Smart Locker frontend's Vietnamese text was double-encoded (UTF-8 read as CP1252) by commit 00f565b; AdminTab.jsx and LockerNetworkMapTab.jsx were repaired to 0 mojibake, so Vietnamese text written to project files must be checked for encoding after writing.
- In Smart Locker the physical lockers are online and publish MQTT status on their own: after a DB reset, a real device (e.g. LOCKER_HN_02 reporting has_item:1) can set a compartment back to OCCUPIED, so cleaning the DB is not final while devices are running.
- The user approved giving the shipper its own GIS map tab for delivery work instead of reusing Admin's LockerNetworkMapTab, taking only ideas 1, 2 and 3 (route order over lockers, locker choice, delivery progress), dropping ideas 4 and 5.
- For the Smart Locker admin map tab (LockerNetworkMapTab), the user chose ideas 1, 2, 3 and 4 from the Bot's proposal (station health map, real KPIs, heartbeat-based online status, emergency unlock with 2-step confirmation) and not 5-6; frontend only, reusing APIs already built in phase 7.
- The user chose to add triggered_by and order_id columns to Smart Locker's command_logs so the log shows who opened a locker and for which order; orders has no shipper column (only shipper_reserved_at), so 'which shipper delivered' cannot be shown yet.
- For the Smart Locker demo, the user chose to keep the fabricated CUSTOMER_OTP row in command_logs as a sample showing the 'Người mở' column (real name + phone), while old rows with NULL stay as 'Không rõ (dữ liệu cũ)'.
- The user wants a locker maintenance feature for the admin account in Smart Locker, possibly placed inside the existing GIS station-map tab; maintenance state must be shown as clearly different from 'lost connection'.
- For Smart Locker locker maintenance the user chose ideas 1-4 of the six proposed (lock a single compartment with a maintenance reason, lock the whole locker, MAINTENANCE marker on the GIS map kept visually distinct from lost connection), and dropped ideas 5-6.
- The Smart Locker project keeps its graduation-report documents in a 'tài liệu đồ án' folder with 5 files (incl. Đánh giá tổng quan.docx); the user wants them updated from the current web app, not kept as they are.
- Smart Locker's real state per the doc fix: Spring Boot 4.0.8 with opaque tokens in auth_sessions (no JWT), 10 stations, 5 locker states (incl. unknown and maintenance), 30 endpoints, no WebSocket (REST polling every 2s/6s).
- The user wants Smart Locker's shipper delivery flow to give the shipper the locker choice: the order must store the customer's address, the system suggests lockers near that address, and the shipper picks among them; this changes code, not only documents.
- The user redirected the Smart Locker project from an e-commerce web app (customer-driven, with cart and checkout) to a delivery-oriented web app: the shipper has the initiative and picks the locker/compartment, while the customer only receives the goods and there is no checkout.
- In Smart Locker only the locker with device id Tu_1 (formerly khuon_vien, LOCKER_HN_01, the PTIT locker) is real hardware; the other 9 lockers on the web are virtual and must always show as connected, while only the real locker's heartbeat is genuinely monitored.
- In Smart Locker, a Leaflet map that only calls invalidateSize in a one-off setTimeout (200ms) loads tiles in just one corner and draws the polyline outside them; ShipperRouteMap was fixed by adding the same ResizeObserver that LockerMap already uses.
- The user expects Smart Locker's shipper route map and distance to use real road routing, not straight-line haversine (20–60% off in Hanoi), and chose to call OSRM (router.project-osrm.org) for polyline and km with an explicit fallback rather than self-hosting a router.
- The user removed the 60-second expiry from Smart Locker's shipper QR: it is one single fixed code per shipper, identical at every verification, and the session after scanning has no time limit at all (not 10 or 30 minutes) — a security risk accepted and to be documented in the security docs.
- The real Smart Locker firmware connects to broker.emqx.io on port 8883 with TLS (mqtts) and MQTT 5.0; the backend has used the same ssl:// 8883 setting since GĐ58, the old tcp 1883 configuration is gone.
- The user's Smart Locker repo has a rollback point: tag v1.0-baove at commit f1f8b53, pushed to origin, plus a verified DB backup under backups/ (gitignored), both created before the improvement phases began.
- Another bot group, 'Lập trình (Kiến · Code · Soát · Vận)' (see docs/TEAM-BRIEF.md), also edits the Smart Locker repo and adds features (e.g. the Kiosk event for the shipper web), so uncommitted/new changes may be theirs — check git log, author and file mtime before assuming they are this team's.
- The user wants Smart Locker work pushed up to the GitHub develop branch (origin/develop), not left sitting unpushed on main.
- For Smart Locker's shipper web the user wants firmware events (shipper verified/rejected, order valid/invalid, compartment selected) polled from the backend's kiosk-events API and shown as popups; the old 4-step deposit progress bar was dead code and was removed, not to be rebuilt.
- The user decided Smart Locker no longer distinguishes S/L compartment sizes: all compartments are the same size, so size is removed from code, DB and UI, and the ESP32 dock/board section is removed from the frontend.
- The user wants Smart Locker's add-order feature to let the shipper attach an order to any customer account (the DB has 3: khachhang/Đoàn Viết Hoàng, nguyenvana, qviet) instead of hard-coding Đoàn Viết Hoàng; the list must come from a real API, not fixed names.
- The user wants Smart Locker's locker pre-booking to offer a selectable hold time per order (1h or 2h), so the expiry is stored on each order (reserve_expires_at) rather than a single global 120-minute constant that would also change old orders.
- In Smart Locker's customer web the user no longer wants the QR/OTP to pop up automatically when the locker reports receive/method; a notification should arrive in the bell dropdown instead, and clicking it opens the QR or OTP popup.
- The user wants the order list on Smart Locker's customer account page sorted by order date, newest first.
- The user requires Smart Locker's MAINTENANCE state to block the shipper from depositing into that locker — the check must be in the deposit path itself, not only in locker suggestion/assignment.
- The user sometimes powers off the Smart Locker hardware, leaving the only real locker (Tu_1/LOCKER_HN_01) OFFLINE; tests then must publish via mqtt-probe or use one of the 9 virtual lockers, because the real locker fails the 5-minute heartbeat rule with a misleading 409.
- The user chose direction A for Smart Locker's deposit path: a deposit is rejected when a real locker's heartbeat is older than the 5-minute rule, while the 9 virtual lockers are always allowed through.
- The user wants Smart Locker's customer account page to update by itself after a pickup: show a 'pickup successful' popup and refresh the order data, with no manual page reload.
- For Smart Locker's customer map tab the user chose ideas 1-4: 'Gần tôi' geolocation sorting by real km, real OSRM route reusing routingApi with a fallback label, accent-insensitive search, and a 'lấy được ngay · còn N ngăn' label replacing the disconnection KPI.
- For Smart Locker web animations the user chose ideas 1-5 of the six proposed (fix the 18 dead animate-in/slide-in-from-bottom classes, which are inert because tailwindcss-animate is not installed; skeleton loading; business-flow animations; tab transitions; success popup) and dropped idea 6.
- The user's rule for Smart Locker's locker compartment diagram: the shipper account always shows both compartments; the customer account shows both while the order has not been deposited successfully, and only the compartment holding that customer's order once the deposit has succeeded.
- For Smart Locker, when a customer forgets to pick up and closes the locker door, the user wants the order to go back to 'waiting for customer pickup' and the customer to collect it with a new code generated on the web, the old saved code no longer being used.
- The user decided Smart Locker's admin account may only view overdue orders and has no right to recall them; only the shipper account may recall overdue orders.
- The user wants Smart Locker to notify the customer both when they forget to deposit a parcel and when they forget to pick one up.
- The user requires Smart Locker's overdue-order recall page (shipper account) to hide the open-compartment button until the shipper verification succeeds, showing it only after that.
- Smart Locker: the shipper recall tab's 'Mở Cửa Ngăn' button must really open the locker like 'Mở khẩn cấp' — call a backend API that sends OPEN_DOOR over MQTT at once, as a new shipper-only API, and the later 'Đã Lấy Hàng & Đóng Cửa' step must not open the door again.
- The user finds Smart Locker's current web UI unsuitable (it reads like a shopping app) and chose the 'operations dashboard' (Bảng điều khiển vận hành) direction for the redesign, putting the locker at the centre of the screen.
- For Smart Locker the user approved the GĐ50 root fix (assigned to sóc): the backend must not publish to the real locker's own uplink topics, and must ignore retained MQTT messages for sensor data and heartbeats, so a backend restart cannot resurrect fake 850 g weights or heartbeats.
- The user chose option A (a locker compartment) as SmartLocker's logo, replacing the old logo in the sidebar, login page and favicon, keeping the 'SmartLocker' wordmark and the blue colour.
- The user dislikes technical decoration in Smart Locker's UI and wants it removed on every page and role: protocol labels (MQTT 8883 TLS, Leaflet GIS, BCrypt Demo), heartbeat chips, project badges, and instructional/descriptive filler lines under titles, in empty states and in QR popups.
- The user removed Smart Locker's shipper 'Theo dõi tủ thật' block; a step bar replaces it with one step per real locker operation (choose order → shipper QR → order QR → pick compartment & deposit → close door), and locker-reported errors show as a red line under it.
- Test data must be cleaned after runs so the shared demo DB returns to its baseline (0 orders, 0 pickup credentials, 20/20 compartments EMPTY), not left with leftover test orders or credentials.
